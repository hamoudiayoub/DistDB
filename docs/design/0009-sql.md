# 0009 — The SQL layer

> Draft written while building Phase 8. The theme is "a relational database is a function from
> SQL text to key-value operations": tables become ordered keys, a query becomes a tree of
> iterators over them, and a SQL transaction is a Phase 7 transaction. The parts to defend without
> notes are the key layout, why a schema change is write skew under snapshot isolation (and the
> fence that fixes it), and the plan for a join.

## Problem

Phases 1–7 built a transactional, sharded, replicated key-value store. Applications speak SQL,
through drivers that speak PostgreSQL's wire protocol. Phase 8 puts a SQL layer on every node:

- `psql` or JDBC connects to **any** node and runs `CREATE TABLE`, `INSERT`, `SELECT` with joins,
  `GROUP BY`, `ORDER BY`, `UPDATE`, `DELETE`, and `BEGIN`/`COMMIT`/`ROLLBACK`;
- results match PostgreSQL's, value for value;
- every SQL transaction is a Phase 7 transaction: snapshot isolation across ranges, whatever
  crashes.

## The shape

```
 psql / JDBC ──pgwire v3──▶ PgServer (distdb-pgwire): one virtual thread per connection
                               │ SQL text, parameters
                               ▼
 Session (distdb-sql)   Lexer ─▶ Parser (recursive descent + Pratt) ─▶ AST (sealed records)
                          ─▶ Binder (names, types, scopes) ─▶ logical plan
                          ─▶ Planner (pushdown, access paths, join algorithms) ─▶ physical plan
                          ─▶ Volcano iterators, on this node (the gateway)
                               │ get / scan / put / delete
                               ▼
 KvTxn ─────────────────▶ Phase 7 Txn: snapshot reads, buffered writes, Percolator commit
```

| Piece | Where | What it does |
|---|---|---|
| `Lexer`, `Parser`, `Ast` | `sql.parse` | text to a tree of sealed records |
| `Type`, `Values` | `sql.types` | five types, PostgreSQL's arithmetic and text output |
| `Catalog`, `TableDesc` | `sql.catalog` | table and index definitions, stored as keys, cached per version |
| `RowCodec` | `sql.encoding` | rows and index entries to keys and values |
| `Binder`, `Planner` | `sql.plan` | names and types; logical to physical plans |
| `Operators` | `sql.exec` | the iterators: scans, joins, aggregation, sort, limit |
| `Session` | `sql` | statements, transactions, retries, prepared statements |
| `KvStore`, `TxnKvStore` | `sql.kv` | the seam to Phase 7, synchronous for the SQL code |
| `PgServer` | `distdb-pgwire` | the PostgreSQL wire protocol, simple and extended query |

## Tables as keys

Every SQL key is a tuple in Phase 1's order-preserving encoding, so **key order is SQL order**,
column by column, for every type:

```
/{table id}/1/{pk columns}                     → the row's other columns   (the primary index)
/{table id}/{index id}/{columns}/{pk columns}  → (empty)                    (a secondary index)
/{table id}/{index id}/{columns}               → the primary key           (a unique index)
```

- A table without a `PRIMARY KEY` gets a hidden `rowid`: the inserting transaction's start
  timestamp (unique cluster-wide, from the TSO) and a counter.
- A row's value lists `(column id, value)` for its non-NULL columns. A missing column reads as
  NULL, so a column added later needs no rewrite.
- A unique index whose columns include a NULL is stored like a non-unique one (with the primary
  key appended): PostgreSQL allows many NULLs in a unique index.
- `-0.0` is stored as `0.0`, so a key equal in SQL is equal in bytes.

A row and its index entries are written by one transaction, so they never disagree.
**Uniqueness costs nothing extra**: two transactions inserting the same key both write it, and
Phase 7's first-committer-wins rule refuses the second at prewrite. A unique index works the same
way through its entry's key.

A scan of a whole table is a key range, `[/{table id}/1, /{table id}/2)`; an index lookup is a
narrower range, then a get per primary key.

## The catalog

Descriptors are keys too, in the reserved table 1:

```
/1/"version"          → catalog version, bumped by every schema change
/1/"next_id"          → the next table id (100 and up)
/1/"names"/{name}     → a table's id, or an index's table and index ids
/1/"desc"/{table id}  → the table's descriptor: columns, types, indexes and their states
```

Every SQL transaction reads `/1/"version"` in its own snapshot, and reloads the descriptors when
it differs from the node's cache. So a transaction always uses the schema of its own snapshot.
DDL runs in transactions too: two `CREATE TABLE`s of the same name both write `/1/"names"/{name}`,
and one fails.

### Schema changes are write skew

`CREATE INDEX` must add an entry for every row, including rows that other transactions are writing
at that moment. Done as one transaction it breaks:

```
T1 (DML)  start 100: reads the schema (no index yet); inserts row r
T2 (DDL)  start 101: adds the index; scans the table (r not committed yet); writes entries; commits
T1        commits at 103: row r, but no index entry. The index is now missing a row, forever.
```

T1 read the schema and wrote a row; T2 read the rows and wrote the schema. They wrote different
keys, so snapshot isolation lets both commit: **write skew**.

F1 and CockroachDB fix this by moving the index through states (absent, write-only, public) with
leases that bound how long a node may use an old schema. DistDB already has the bound it needs:
Phase 7's **transaction floor**. A range refuses prewrites from transactions that started below
its floor, and lock resolution rolls back their unfinished locks.

`CREATE INDEX`:

1. **Write-only.** A transaction adds the index in state WRITE_ONLY: from now on, writers maintain
   it, readers don't use it. It commits at `C1`.
2. **Fence.** Raise the floor to `C1` on every range, then resolve every lock below `C1`. After
   this, no transaction that started before `C1` (with the old schema) can still commit, and every
   one that had locked keys has finished. *(The same walk as the GC worker's, with `C1` for `G`.)*
3. **Backfill.** A new transaction (start `S > C1`) scans the table at `S` and writes the missing
   entries. Each row was written either before `S` (so the scan sees it) or by a transaction that
   started after `C1` (so that transaction wrote its own entry). For a `UNIQUE` index it also
   checks for duplicates. It marks the index PUBLIC and commits.

A writer that races with the backfill on the same row writes the same index key, so one of them
gets a write conflict and retries. Old transactions caught by the fence fail with a retryable
error (SQLSTATE `40001`).

`DROP INDEX` and `DROP TABLE` run the same way: remove the definition and commit at `C1`, fence,
then delete the keys. No writer with the old schema can add new ones afterwards.

## The pipeline

**Parser.** Hand-written recursive descent for statements, with Pratt parsing (binding powers)
for expressions, following PostgreSQL's precedence:

```
OR < AND < NOT < IS < comparisons < BETWEEN, IN, LIKE < || < + - < * / % < unary - < ::
```

The AST is sealed interfaces of records, so the binder's `switch`es are checked for exhaustiveness
by the compiler.

**Binder.** It resolves names in scopes:

- a FROM clause builds a scope of qualified columns;
- a subquery's scope points to its outer scope, and a column found there becomes an *outer
  reference* (a correlated subquery);
- `GROUP BY` switches to an aggregate scope, where every column must be grouped or aggregated
  (otherwise error `42803`).

Types follow PostgreSQL:

- an integer literal is INT and `1.5` is NUMERIC;
- a quoted literal stays UNKNOWN until its context gives it a type;
- INT op NUMERIC is NUMERIC, and anything with FLOAT is FLOAT.

**Planner.** It turns the logical tree into a physical one:

- **Predicate pushdown:** WHERE conjuncts move below joins to the side they reference.
- **Access paths:** for a scan with conjuncts on a key prefix, an equality on the full primary
  key becomes a point get. A prefix or a range becomes a narrower scan of the primary key or of an
  index. Otherwise the scan reads the whole table.
- **Joins:**
  - an equi-join becomes a **hash join** (it builds the right side);
  - when the right side is a table keyed by the join columns and the left side looks small (a point
    or index lookup), it becomes a **lookup join**, one get per left row;
  - anything else is a **nested loop**.

  Without statistics, "looks small" is a rule of thumb; Phase 9 brings costs.

`EXPLAIN` prints the physical plan.

**Executor.** Volcano iterators: `open`, `next` (one row, or null at the end) and `close`. There are
operators for scan, point get, index scan, filter, project, the three joins (inner, left, right and
full), hash aggregation, sort, limit, distinct, set operations and VALUES.

A subquery is planned once and run when an expression needs it. An uncorrelated one runs once per
statement; a correlated one runs again for each outer row.

**Why synchronous?** Phase 7's client is asynchronous (`CompletableFuture`). The SQL code is
synchronous, which keeps the iterators simple, and waits through an `Awaiter`:

- in a server, each connection has a virtual thread, and waiting is `join()`;
- in the simulator, each session is a **fiber**: a thread that runs only while the simulation's
  thread waits for it. Waiting hands control back, and the future's completion (a simulation task)
  hands it to the session again. One thread runs at a time, so a seed replays exactly, and many
  sessions can be mid-statement at once. A first design, where a wait ran the simulation from
  inside the waiting statement, nested sessions in each other's waits and starved the outer ones
  (see the journal).

## Types and values

| SQL | Java | Text output (as PostgreSQL) |
|---|---|---|
| `BOOLEAN` | `Boolean` | `t`, `f` |
| `INT`, `INTEGER`, `BIGINT`, `SMALLINT` | `Long` (64-bit; overflow is error `22003`) | `42` |
| `DOUBLE PRECISION`, `FLOAT`, `REAL` | `Double` | shortest exact digits; `1e+15` from 10^15 and below 10^-4 |
| `NUMERIC`, `DECIMAL` | `BigDecimal` | scale kept: `2.50` |
| `TEXT`, `VARCHAR(n)` | `String` | as is |

NUMERIC follows PostgreSQL's scale rules:

- addition keeps the larger scale and multiplication adds the scales;
- division uses `select_div_scale`: at least 16 significant digits, so `1/3.0` is
  `0.33333333333333333333`;
- `avg` of integers is NUMERIC.

`round` on NUMERIC rounds half away from zero, and on FLOAT half to even. Integer division
truncates toward zero. Text sorts in byte order (collation `C`).

## Transactions

- **Autocommit:** a statement outside `BEGIN` is a transaction. If it fails in a way a retry may
  fix (a conflict, an abort, a fence), the session runs it again from scratch, up to ten times.
  This is safe because no row has been sent yet.
- **Explicit:** `BEGIN` takes a start timestamp. Statements read the snapshot plus the
  transaction's own writes, which stay buffered in the client until `COMMIT`. After an error, the
  transaction is *aborted*: every statement fails with `25P02` until `ROLLBACK`, like PostgreSQL. A
  conflict at `COMMIT` is `40001` (*could not serialize access*), and the client retries the whole
  transaction. An unknown outcome (a timeout after the commit point may have passed) is `40003`.
- **Isolation** is snapshot isolation: PostgreSQL's `REPEATABLE READ`. Write skew is possible, as
  in PostgreSQL at that level.
- `UPDATE` and `DELETE` collect their target rows before writing. A statement never sees its own
  writes, which avoids the Halloween problem.

## pgwire

PostgreSQL's protocol v3, one virtual thread per connection.

- **Startup:**
  - a TLS or GSS request is answered `N`;
  - authentication is trust (no passwords yet);
  - the server reports its parameters (`server_version`, `client_encoding=UTF8`,
    `standard_conforming_strings=on`, ...).
- **Simple query (`Q`):** `psql` uses it. One query string can hold many statements; each gets
  its own results.
- **Extended query (`P`/`B`/`D`/`E`/`S`):** JDBC uses it for everything.
  - Parameters `$1..$n` get their types from context; values arrive as text or binary.
  - Results are text or binary, as asked.
  - After an error, messages are skipped until `Sync`.
- **ReadyForQuery** carries the transaction state (`I`, `T` or `E`), which `psql` shows in its
  prompt.

## Verification (the Phase 8 gate)

**Results match PostgreSQL.** The sqllogictest files hold the results a real PostgreSQL 18 gave,
recorded with `-Ddistdb.slt.complete=<jdbc url>` (`SqlLogic.complete`): query results printed by
type (`I`, `R` with three decimals, `T` exact text), and the SQLSTATE of every expected error.

- 11 hand-written files cover tables, types and NUMERIC scale, NULL logic, selects, all joins,
  aggregation, subqueries, set operations, writes, indexes and transactions.
- `fuzz.test` holds 400 random queries from `SqlFuzz` (seed 1): filters, every join kind,
  grouping, correlated subqueries, set operations, over two tables with NULLs, duplicates and
  indexes.
- In all, 162 statements and 619 queries. DistDB gives PostgreSQL's answers on one node
  (`SqlLogicTest`, over an in-memory store with the same isolation) and on the simulated sharded
  cluster (`SqlLogicSimulationTest`: three PD nodes, three data nodes, Raft, Percolator).

**Correct under faults: `SqlBankSimulationTest`.** It runs a bank in SQL on Phase 6's faulty
cluster (partitions, power cuts of data nodes and the PD leader, disk failures, stalls, forced
splits and moves, GC). Three to eight sessions, on one to three gateways, run:

- multi-statement transfers (`BEGIN`, read, two updates, `COMMIT`, with pauses between);
- single-statement transfers (one `UPDATE` of two rows, guarded by a subquery);
- owner changes (an indexed column), and openings and closings of empty accounts (inserts and
  deletes);
- audits (`count`, `sum`, `min` in one statement);
- index audits (an index lookup and a full scan, in one snapshot).

An admin session builds, drops and rebuilds the owner index under that load, and tries a unique
index that must fail.

Every session is a fiber (`SimFibers`): a thread that runs only while the simulation's thread waits
for it. One thread runs at a time and a seed replays exactly, yet the sessions' statements
interleave at every wait, as real clients' would.

Checks:
1. every audit holds the opening total, and no balance is negative;
2. an index lookup and a full scan of the same snapshot always agree;
3. afterwards every public index has exactly one entry per row, at the row's values (read raw);
4. no error but those the faults explain (40001, 40003, 58000, and 23505 from the doomed unique
   index);
5. the cluster's own checks: replicas converge, the same entry at each index everywhere, no
   overlapping replicas.

- **Gate:** **1,000 seeds pass** (about 2.5 seconds per seed):
  - **Money:** 15,345 transfers committed, 3,568 accounts opened and 2,488 closed. All 8,571
    audits found the opening total, and all 6,332 index audits agreed with a full scan.
  - **Schema changes under load:** 1,303 index builds and 303 drops. Faults cut 392 builds short,
    and each was dropped and rebuilt.
  - **Faults:** 10,571 power cuts, 10,463 partitions and 5,605 disk failures, with 11,749 splits
    and 621,110 membership changes.
  - **Errors sessions saw:** 6,889 serialization failures (conflicts and fences), 331 unknown
    outcomes and 3,872 timeouts, all among those the faults explain.

  CI runs 10 seeds.

- **`SqlClusterTest`** (real processes): three PD JVMs and three data nodes with `--sql`. JDBC on
  three different nodes creates tables, joins, aggregates, builds an index used through another
  node, and hits a cross-node conflict (40001); then `psql` runs a script with transactions and a
  join.
- **`PgServerTest`:** PostgreSQL's JDBC driver, in text and binary modes, with prepared statements,
  transactions, error codes, suspended portals and `RETURNING`.
- **`SessionTest`:** plan choices (through `EXPLAIN`), prepared statements, isolation across
  sessions, the fence, `DROP TABLE` cleanup, NUMERIC keys, and indexes agreeing with rows after
  random writes.
- **`FenceTest`:** after `fence(ts)`, a transaction that prewrote below `ts` cannot commit.
- **`RowCodecTest`:** key order equals SQL order, for every type, as properties.

**Planted bugs** (one at a time; the unit tests, then 60 bank seeds):

| Bug put in on purpose | Unit tests | Bank simulation |
|---|---|---|
| P1: `CREATE INDEX` without the fence | `SessionTest` | seed 21: the index found 3 rows, a scan 4 |
| P2: inserts skip WRITE_ONLY indexes | — | seed 8: the index found 2 rows, a scan 3 |
| P3: `UPDATE` leaves the old index entry | `SessionTest`, sqllogictest | seed 6: an entry for no row |
| P4: a point get drops the rest of the WHERE | `SessionTest`, sqllogictest | — |
| P5: `x NOT IN (..., NULL)` is false, not NULL | sqllogictest | — |
| P7: `INSERT` skips the primary-key check | `SessionTest`, sqllogictest | — |
| P8: a hash join ignores the rest of its ON | sqllogictest | — |
| P9: `avg` rounds to two decimals | sqllogictest (PostgreSQL's scale) | — |
| P10: the fence raises floors but resolves no locks | `FenceTest` | — (60 seeds) |

What the misses say:

- **P2 first survived the bank too:** its workload had no INSERTs, only updates, which maintain
  every index. Opening and closing accounts was added, and seed 8 caught it.
- **P10 is a narrow race:** a transaction must have prewritten before the floor reached its
  range, then commit after the backfill's snapshot. Sixty seeds did not hit it, so `FenceTest`
  states the contract directly.
- **Not planted:** caching a catalog version the transaction wrote itself. That was the bug of
  the counter versions (see the journal). Since versions became the writer's start timestamp, a
  cached uncommitted version can never match a committed one, so the check is only an
  optimization.
